使用 说明

一句话介绍：AI 测试官是一个「会自动跑测试的 AI 助手」。你告诉它代码仓库和要检查什么， 它会真实地把测试跑一遍（不是瞎猜），然后给你一份「能不能合入/发布」的结论报告。

一、它能干什么（五个场景）

场景一句话说明回答的问题什么时候用
A · 代码改动测试改了哪些文件，就只跑相关测试「这改动安全吗？」提交 MR / PR 前
B · 需求覆盖检查给需求文档，查代码实现 + 测试覆盖了没「需求落地了吗？」需求评审、提测前
C · 持续巡检对分支全量跑测，失败就告警「系统还健康吗？」放在流水线里定时跑
D · Bug 修复验证先在旧分支复现 bug，再在新分支验证修好「bug 真修好了吗？」修复缺陷后、关闭工单前
E · 合并前检查模拟合并两个分支再跑测，抓「各自都对、合起来就错」「能安全合并吗？」多分支并行开发合并前

和传统测试工具的区别：

  • AI 理解，不是机械执行：它会读你的改动，理解「改了什么、为什么改」，再决定跑哪些测试；
  • 真实跑测，不是嘴炮：所有结论都来自在隔离环境里真实执行的测试，附证据；
  • 给结论，不是给日志：报告直接告诉你「能合 / 不能合 / 为什么」。

二、快速上手（网页版）

打开我们的长期访问链接：

http://86820782946dd2a09a6236df48cf9edd.makers-preview.qcdntest.net/

页面长这样：顶部是 A/B/C/D/E 五个场景标签，下面是参数填写区和一个「运行」按钮。

最快的体验方式（零输入）：

  1. 在「内置案例」下拉框选一个示例（case1 电商优惠券 或 case2 停车场计费）；
  2. 点 「使用内置示例填充」 按钮 —— 所有参数自动填好；
  3. 点 「运行」，等几十秒~两分钟；
  4. 看结果：通过/失败数、问题清单、AI 根因分析，还能打开完整 HTML 报告。
注意：内置案例是我们特意准备的「有 bug 的仓库」，每个场景都埋了问题，所以正常运行就应该抓到问题——这说明它真的在干活，详见第四节。

可选：把结果推送到企业微信群

页面「高级选项」里有一个全局可选的「企微 webhook」输入框。填了它，每次运行结束后会自动把结论推送到你指定的企业微信群（不填就不推送，不影响任何功能）。

怎么拿到这个 webhook 地址（30 秒）：

  1. 在企业微信里打开你想接收通知的群 → 右上角「…」→「群机器人」→「添加」；
  2. 给机器人随便起个名字（如「AI 测试官」），创建后会生成一个 https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxxxxxxx 格式的地址；
  3. 复制这个地址，粘贴到页面的「企微 webhook」框里，再点运行。

跑完后群里就会收到机器人推送的消息：场景、通过/失败统计、问题清单摘要。适合场景 C（持续巡检）这类「跑完没人盯着看」的用法——出问题了群里自然会响。

三、五个场景详细用法

场景 A · 代码改动 → 针对性测试

解决什么：传统做法改一行代码也要全量跑几百个测试，慢且浪费。场景 A 让 AI 读改动 diff，只挑跟改动相关的测试跑。

参数含义示例
公开仓库 URL你的 git 仓库地址（可留空用内置案例）https://github.com/owner/repo.git
base 分支改动前的分支main
target 分支改动后的分支feature/coupon-bug

你会看到：改动意图分析（AI 总结的）、风险等级、挑了哪些测试、每个测试通过/失败、失败项的 AI 根因。

结果怎么读：失败项会标注严重级别（P0/P1/P2）。出现 P0 阻断项 = 这个改动不能合。

场景 B · 需求文档 → 覆盖度检查

解决什么：需求写了 10 条，开发实现了几条？测试又覆盖了几条？人工核对又慢又容易漏。

参数含义说明
公开仓库 URL被测仓库同上
需求文本粘贴需求原文自由文本即可，AI 自己拆解；留空则用内置示例需求

需求文本写法建议（写得越清楚，AI 拆得越准）：

## 模块：src/pricing.js
### 测试点 P1：停车不超过 15 分钟免费
关联用例：15 分钟内免费
  • ## 模块：<源码路径> —— 声明这个需求点属于哪个文件；
  • ### 测试点 Pxx：<描述> —— 一条可验证的需求点；
  • 关联用例：<测试名子串> —— 可选，写了就能精确核对某条测试是否存在。

你会看到：一张覆盖度矩阵 —— 每个需求点是 已实现已覆盖 已实现没测试 没实现。

场景 C · 持续巡检

解决什么：代码放着不动也会「腐化」（依赖升级、被人误改）。定时全量跑一遍，有问题立刻推送告警。

参数含义
公开仓库 URL被测仓库
target 分支要巡检的分支
企微 webhook（可选）填了之后，跑完自动把结果推送到企业微信群

典型用法：拿 API 地址（见第七节）挂到你们的定时任务/流水线里，每天跑一次。

场景 D · Bug 修复验证

解决什么：开发说「bug 修好了」，测试怎么确认？场景 D 自动做对照实验：在有 bug 的分支上跑（应该失败，证明 bug 真实存在），再在修复分支上跑（应该通过，证明确实修好了），还会检查有没有顺手改坏了别的东西（回归）。

参数含义示例
base 分支有 bug 的分支feature/free-window-bug
target 分支修完后的分支fix/parking-pricing

你会看到：修复判定三选一 ——

  • fixed旧分支失败、新分支通过，bug 确已修复；
  • partial部分修好（报告会列出哪项证据链断了）；
  • not_fixed新分支上依然失败，没修好。

场景 E · 合并前检查（语义冲突检测）

解决什么：最容易被忽视的一类 bug —— 分支 A 自己跑全过，分支 B 自己跑也全过，但合在一起就出错。git 的文本合并发现不了这种问题（没有文本冲突），但逻辑上互相踩了。

参数含义示例
target 分支要合并的分支 Afeature/peak-member-pass
merge 分支要合并的分支 Bfeature/peak-analytics-guard

它会做三件事：

  1. 分支 A 独立跑一遍、分支 B 独立跑一遍（都应该全过）；
  2. 在临时工作区把两个分支模拟合并（不污染你的仓库），再跑一遍；
  3. 对比找出「合并后才新出现的失败」，并让 AI 解释两个分支为什么打架。

你会看到：先报 git 文本冲突（如果有）；文本合得上但逻辑冲突的，列出语义冲突清单 + AI 冲突原因分析。

四、用内置演示案例体验

我们准备了一个公开的演示仓库（GitHub：guokeqianhg/HACK_case），里面有两套案例，每套都在五个场景里故意埋了问题——所以你跑出来「发现 bug」才是正确的演示效果：

case1 · 电商优惠券系统

场景埋的问题预期结果
Afeature/coupon-bug 分支改坏了优惠券计算精准选测抓到计算错误 + AI 根因
B需求文档里有的功能没测到覆盖度矩阵出现盲区项
Dfeature/coupon-bug（有 bug）→ main（已修复）判定 fixed，附 fail→pass 证据
E两个优惠券分支合并后逻辑打架抓到文本/语义冲突 + AI 双分支解释

case2 · 停车场计费系统

场景埋的问题预期结果
Afeature/free-window-bug 把免费时长 15 分钟改成了 5 分钟抓到断言失败 + AI 根因
B需求 P9（前端查询页）没有对应测试报测试盲区 untested
Dbug 分支 → fix/parking-pricing 修复分支判定 fixed
E「高峰会员放行」+「高峰统计」两分支各自全过，合并后统计数对不上（3 ≠ 2）抓到 1 个语义冲突 + AI 解释

case3 · 真实公开开源仓库实测（通用性验证）

case3 和 case1/case2 不同：它不内置任何代码，被测对象是 GitHub 上真实的开源库——用来证明 AI 测试官不是「只能跑自家示例」，给个公开仓库地址 + 分支就能跑。

被测对象（都是测试用 node:test 编写、零第三方依赖、release tag 完整的小型库）：

仓库是什么看点
https://github.com/wooorm/trough.git中间件链库版本升级对比（2.1.0→2.2.0）
https://github.com/wooorm/bail.git错误短路工具1.x→2.x 真实的 CJS→ESM 破坏性升级

怎么跑：「公开仓库 URL」直接填上面任意一个地址（不点内置填充），分支参数示例：

场景参数预期结果
Abase=2.1.0 target=2.2.0（trough）小版本升级，安全通过
Abase=1.0.5 target=2.0.2（bail）AI 读懂「CJS→ESM 迁移、破坏性变更、风险 high」；抓到的失败能正确归因「缺依赖（环境）」而非「代码错」
Ctarget=main健康基线通过
Dbase=2.0.0 target=2.2.0（trough）修复就绪
Ebase=2.1.0 target=2.2.0 merge=2.0.2正确拦截：老版本自身测试就失败，不误判「合并安全」
小技巧：tag 可以直接当分支填（--base 2.1.0），分支 / tag / commit 都能作为对比对象。

什么样的公开仓库能跑（硬条件）：Node.js 项目；测试用 node:test 编写、文件名符合 *.test.js 约定；零依赖或仅自引用（云端不会执行 npm install）；公开可 clone。没有前端/UI 的仓库会自动跳过对应检查，只跑单测。

注意：知名开源库的正式 release 大多是健康的，所以 case3 多数场景得到「通过」结论——这本身就是正确结果，证明它不会乱报假警报；想看「抓 bug」的戏剧性效果请用 case1 / case2。
演示建议：最有冲击力的是 case2 场景 E——「两个分支各自测试全过，AI 却告诉你合并不了」，最能体现和普通测试工具的差别。

五、测你自己的仓库

把「公开仓库 URL」换成你自己的 git 地址即可（GitHub / 工蜂等公开可 clone 的地址）：

https://github.com/你的账号/你的仓库.git

注意事项：

  1. 仓库必须公开可 clone（演示环境没有你的私有凭据）；
  2. 分支名要填仓库里真实存在的（base / target / merge 都是分支名或 commit）；
  3. 场景 A/D/E 的分支组合要符合语义（比如场景 D 的 base 是「有 bug」、target 是「修复后」）；
  4. 仓库里要有可运行的测试（引擎会自动发现 tests/、test/ 下的测试文件并用 node 跑）；如果你的项目是前端页面，引擎还会尝试做 UI 冒烟；
  5. 首次运行要 clone 整个仓库，大仓库会慢一些，请耐心等待。

七、其他使用方式

前置说明：HTTP API 调的是我们已部署好的云端服务，开箱即用；而 MCP Server 和本地命令行是「把引擎拿到你自己机器上跑」（和云端无关），需要先把本项目代码 clone 下来： 
git clone https://github.com/guokeqianhg/HACK.git
cd HACK
前提：机器上装好 Node.js（v18+） 和 git；后续所有 node agent/... 命令都在这个 HACK 目录下执行。想测私有仓库也只能走这两种方式（用的是你本机的 git 凭据）。

1. HTTP API（集成到你们自己的系统）

curl -X POST "http://86820782946dd2a09a6236df48cf9edd.makers-preview.qcdntest.net/test-officer" \
  -H "Content-Type: application/json" \
  -H "makers-conversation-id: my-session-001" \
  -d '{"scenario":"E","params":{"demoCase":"case2"}}'
  • scenario：A/B/C/D/E 五选一；
  • makers-conversation-id：平台要求的会话编号，自己随便起（6~36 位字母数字，如 test-001），用于把多次请求归入同一会话；
  • params：就是网页上那些输入框的内容写成 JSON，对应关系如下：
params 字段对应网页输入框哪些场景用含义
demoCase「内置案例」下拉框均可（可选）"case1" / "case2"，用内置演示仓库；填了它就不用填 repoUrl
repoUrl公开仓库 URL测自己仓库时必填git 地址
basebase 分支A、D、E基准分支（场景 D 里 = 有 bug 的分支）
targettarget 分支A、C、D、E目标分支（要验证的那个）
mergemerge 分支仅 E要合并的第二个分支
requirementText需求文本仅 B需求原文（留空用内置示例需求）
webhook企微 webhook均可（可选）跑完推送结果到企业微信群

举例：网页上「选场景 E + 案例 case2 点运行」，和发 API {"scenario":"E","params":{"demoCase":"case2"}} 效果一模一样。

返回 JSON：含 summary（统计）、reportHtmlContent（完整报告 HTML 字符串）等。

2. MCP Server（接到任意 MCP 客户端）

它是干嘛的：MCP 是「给 AI 客户端装插件」的标准协议。把我们的引擎以 MCP Server 形式跑在你自己的机器上（需先按本节开头 clone 代码），之后 CodeBuddy / Claude 这类 AI 客户端就能用自然语言直接调用，比如说一句「帮我跑一下场景 E」——不用开网页、不用记参数。

本项目自带标准 MCP Server（agent/mcp-server.mjs），暴露 3 个工具：list_scenarios / run_test_officer / get_report。

# stdio 模式：不开端口，由 AI 客户端当子进程拉起（在客户端配置里填这条命令）
node agent/mcp-server.mjs

# HTTP 模式：变成 http://127.0.0.1:3001/mcp，可注册到 Box 平台 MCP 连接器
node agent/mcp-server.mjs --http --port 3001

# HTTP 模式 + 对外开放（别的机器也能访问）：必须设访问密钥，调用方带同样密钥才放行
node agent/mcp-server.mjs --http --port 3001 --host 0.0.0.0 --token <访问密钥>
关于 --token：由启动服务的人（你）自己设置，相当于给服务设个密码；别人调用时要在请求头带 Authorization: Bearer <同一个密钥>，否则一律 401。只在本机用（默认 127.0.0.1）时不需要 token。

客户端里直接说「用 run_test_officer 跑一下场景 E」即可，设 useDemoDefaults=true 零配置体验。

3. 本地命令行（开发者）

# 场景 A：本地仓库 + 本地分支
node agent/run-test-officer.mjs --scenario A --repo sample-app --base main --target feature/xxx

# 场景 E：直接给远端仓库，引擎自动 clone
node agent/run-test-officer.mjs --scenario E --repo-url https://github.com/owner/repo.git \
  --base main --target feature/a --merge feature/b

# 查看全部参数
node agent/run-test-officer.mjs --help

LLM 通过环境变量配置（不配置则自动走离线确定性模式，照样能跑）：

OPENAI_API_KEY=sk-xxx
OPENAI_BASE_URL=https://你的网关地址/v1
AI_GATEWAY_MODEL=kimi-k2.5          # 主模型（理解/根因）
AI_GATEWAY_SMALL_MODEL=deepseek-v4-flash  # 快模型（轻量判定）

八、常见问题 FAQ

Q1：运行一次要多久？
通常 30 秒 ~ 2 分钟。要 clone 仓库 + 跑真实测试 + AI 分析，请耐心等待，不要重复点运行。

Q2：为什么会「发现 bug」？是不是你们系统有问题？
如果你用的是内置演示案例——那是我们故意埋的 bug，抓到才说明产品工作正常。换成你自己的仓库，报出的问题就需要认真对待了。

Q3：填了仓库地址报错「克隆失败」？
检查：① 地址是不是 git 地址（以 .git 结尾的那种）；② 仓库是不是公开的；③ 稍等重试（跨境网络偶尔抖动，系统会自动重试 3 次）。

Q4：支持私有仓库吗？
网页版/云端版目前只支持公开仓库。要测私有仓库，用「本地命令行」方式（第七节第 3 条），引擎直接用你本机的 git 凭据。

Q5：AI 不配置能用吗？
能。不配置 LLM 环境变量时自动切换离线模式：选测、跑测、出报告都正常，只是「改动意图总结、根因分析、冲突解释」这些 AI 文案会变成模板化描述。

Q6：会修改我的仓库吗？
不会。所有测试都在隔离的临时环境（云端沙箱 / 本地临时目录）里进行，模拟合并也是临时操作，你的仓库一个字符都不会被改。

Q7：一次运行花多少钱？
测试执行本身免费（云端沙箱有免费额度）。AI 分析每次运行只调用 1~4 次 LLM，消耗的是你自己配置的 API Key 额度，量级在几千 token 以内。
